## 项目概述（一句话）

基于 RAG（检索增强生成）的企业知识库智能问答系统，三层分离架构（Vue3 → FastAPI → Spring Boot），支持混合检索、流式对话、Agent 模式，以及权限闭环、操作审计齐备的完整管理后台。

> **RAG 智能知识问答系统** | 独立开发 | 2025-2026
>
> 从零设计并实现企业级 RAG 知识库问答系统（31,000+ 行代码，260+ API 端点，29 张数据表）。采用三层分离架构（Vue3 + FastAPI + Spring Boot），实现向量语义检索与 Lucene BM25 混合检索（MRR 79.6%），配合 Reranker 重排序与父子切片策略。自建 20 条黄金测试集完成检索质量自动化评测，并引入 Embedding LRU 缓存、模型预热及基于向量相似度的语义缓存（Redis），FAQ 命中时端到端延迟从 960ms 降至 50ms。构建 ReAct Agent 系统；管理后台实现跨三层权限闭环（JWT 角色签发 → Java @PreAuthorize → Python 服务端角色门禁 → 前端路由守卫与角色动态菜单）、管理域写操作全量审计、API Key 双轨鉴权与运行时配置热更新，管理级知识库对未授权用户完全不可见。

## ⭐ 详细版：STAR 法则（适合面试口述 / 项目经历栏）

### S — 背景

企业内部文档分散在多个系统（Wiki、共享文件夹、邮件附件）中，员工查找信息需要跨系统搜索，平均耗时 5-10 分钟，且缺乏统一的智能问答入口。

### T — 任务

从零设计并实现一套基于 RAG 技术的企业知识库智能问答系统，覆盖**文档自动解析入库 → 混合检索 → LLM 流式生成 → 管理后台**全链路，要求具备：
- 多格式文档自动解析与向量化索引
- 高召回率的混合检索（语义 + 关键词）
- 低延迟流式对话体验
- 完整的 RBAC 权限与审计体系

### A — 行动

**1. 架构设计**
- 设计三层分离架构：**Vue3 管理前端**（5173）→ **Python FastAPI AI 网关**（8001）→ **Java Spring Boot 检索引擎**（8002），前后端共 240+ API 端点
- 数据库层：MySQL（业务数据，29 张表）+ Redis（缓存/会话）+ Qdrant（向量存储，512 维）+ Lucene（BM25 全文索引）+ SQLite（本地会话降级）

**2. 检索管线**
- 实现**向量语义检索（Qdrant）+ Lucene BM25 关键词检索**的加权混合检索（0.7:0.3），通过 JDK 21 Virtual Thread 并行执行
- 设计**父子切片策略**（child=300字, parent=1000字, overlap=50），小块检索 + 大块生成，兼顾精度与上下文完整性
- 集成 **Reranker 重排序**：检索后对候选结果做 Cross-Encoder 级别的语义相似度二次排序

**3. 对话与智能**
- LLM 调用层封装为可替换的 OpenAI 兼容端点，支持 DeepSeek / vLLM / Ollama 即插即用
- 实现 **SSE 流式输出** + **Self-RAG 自反思验证**（事实核查 + 检索质量评估 + 补充检索闭环）
- 构建 **ReAct Agent 系统**，内置 Web 搜索、代码解释器、文件解析等 5 个工具
- 支持 **MCP 协议**，可作为 Claude Desktop 等客户端的工具服务

**4. 性能优化（本轮落地）**
- **Embedding LRU 缓存**：LinkedHashMap 实现，同一文本向量化仅计算一次，命中时省 50-100ms
- **模型预热**：Spring Boot @PostConstruct 阶段完成 ONNX 模型真实推理预热，消除首次请求 2 秒冷启动
- **语义缓存**：基于余弦相似度（阈值 0.92）的问答缓存，Redis 存储 512 维向量，FAQ 命中时延迟 960ms → 50ms（降低 95%）

**5. 质量保障**
- 自建 **20 条黄金测试集**（基于真实知识库内容），实现检索召回率自动化评测脚本
- 支持 **Recall@K、Hit Rate@K、MRR** 三项指标一键评估

**6. 管理后台**
- 实现完整 **RBAC 权限体系**（用户/角色/菜单三级管理）
- **API Key 管理 + 访问控制 + 限流规则 + 敏感词过滤 + 审计日志**
- **仪表盘**：ECharts 可视化展示文档排行、Token 用量、API 调用趋势
- 支持 **13 种文档格式**自动解析（PDF/DOCX/XLSX/PPTX/MD/TXT/HTML/CSV/XML/RTF 等）

**7. 权限与审计闭环（深度迭代）**
- **跨三层权限闭环**：登录时签发含角色声明的 JWT（Java 每请求查库、Python 读 claims + 无声明回退查库），管理写操作由 Java `@PreAuthorize` 与 Python `require_admin` 双重门禁，前端路由守卫拦截无角色会话——修复了"任何登录用户可操作全部管理接口"的越权漏洞
- **菜单驱动式 UI**：侧边栏由 sys_menu + 角色-菜单授权动态渲染（按角色返回菜单树），菜单管理、角色管理从摆设变为真实控制面
- **知识库三级可见级别的完整落地**：PUBLIC/EMPLOYEE/MANAGEMENT 服务端强制，用户编辑弹窗支持双向同步"可访问知识库"授权；员工端"查看知识库"按权限过滤（未授权的管理级知识库对员工完全不可见，越权预览 403），并移除员工侧全部写操作入口
- **API Key 双轨鉴权**：外部调用方持 `X-API-Key` 经 Java 校验（有效期/禁用/日限额 + 调用计数）后以密钥归属用户身份进入对话链路，与 JWT 路径并存
- **运行时配置热更新**：管理台"系统配置"页参数（检索 topK、敏感词开关等）经 60s 缓存的运行时配置读取器被聊天链路真实消费，改配置即改线上行为
- **全量操作审计**：Java 拦截器统一记录管理域全部写操作（含操作人/IP/成功失败），Python 侧补齐知识库/文档/分块写操作，审计与系统日志语义分离

## 🎯 面试可能的追问 & 应答要点

### Q1: Recall@5 100% 是怎么测的？有没有水分？
> 坦诚说明：20 条测试集、47 个切片的小规模验证，搜索空间小所以召回率高。重点强调 MRR 79.6% 更真实地反映排名质量，以及这套评测体系是可复用的——换一批数据、换一个知识库跑同样的脚本也能得到可比的结果。大规模场景下业界 Recall@5 通常在 75%-92%。

### Q2: 语义缓存怎么实现的？会不会返回过时答案？
> 核心机制：用户提问 → Java ONNX 向量化（512维）→ Redis 中逐条余弦相似度匹配（阈值 0.92）→ 命中则直接返回。TTL 默认 24 小时，问题 MD5 索引防止重复写入，上限 200 条自动淘汰。过时问题：当前 TTL 策略适用于 FAQ 场景；知识库变更时可主动调用 clear 接口清空。

### Q3: 为什么用三层架构而不是单体？
> 关注点分离：Java 负责重型计算（ONNX 推理、Lucene 索引、Qdrant 交互），Python 负责 LLM 编排和 Agent 调度（生态更丰富），Vue 负责管理界面。各层可独立扩缩容、独立部署。Python 网关同时承担统一鉴权和代理转发。

### Q4: 从 962ms 降到 50ms 怎么做到的？
> 这不是通用优化，是语义缓存的命中场景。
> - 正常 RAG 链路：检索 500ms + LLM 生成 500ms ≈ 1000ms
> - 缓存命中：向量化 50ms + Redis 查询 1ms ≈ 50ms
> - 缓存命中率取决于业务场景，FAQ 密集场景预期 30-50%
> - 非命中场景通过 Embedding 缓存和模型预热也能降低 20-30%

### Q5: 权限体系横跨三层，怎么保证判定一致？改了角色何时生效？
> 三层各守一道：Java 侧 JwtAuthFilter 每请求从数据库加载角色配合 @PreAuthorize，永远以 DB 为准；Python 网关读 JWT 角色声明（零查询开销），对改造前签发的旧 token 回退查库兼容；前端路由守卫只做展示层拦截。一致性语义：Java 实时生效，Python 侧窗口 = token 剩余有效期，重新登录立即刷新——这是 JWT 无状态设计的标准取舍，可现场讲清。知识库可见性（PUBLIC/EMPLOYEE/MANAGEMENT）则由服务端统一解析接口裁决并带 60s 缓存，Java 不可达时 fail closed。

### Q6: "运行时配置热更新"具体怎么做？为什么不用配置中心？
> 轻量方案：管理台改 sys_config 表，业务代码经运行时配置读取器消费（进程内 60s 缓存，Java 不可达时回退环境变量默认值，fail-safe）。最迟 1 分钟生效，已实测敏感词开关从"改配置"到"拦截行为变化"的完整闭环。不用 Nacos/Apollo 是因为单机部署引入注册中心的运维成本大于收益——但读取器收敛了全部配置访问点，未来接配置中心只换实现不改调用方。

### Q7: 审计日志和系统日志有什么区别？怎么做到全覆盖？
> 系统日志记录"程序发生了什么"（异常/堆栈），审计日志回答"谁在什么时间对什么做了什么"（带操作人、IP、目标资源、成功失败）。覆盖方式：Java 侧一个 HandlerInterceptor 统一拦截 /api/admin、/api/system、/api/security 下全部非幂等请求，operation 归一化为 CREATE/UPDATE/DELETE 供 UI 按类筛选；Python 侧知识库/文档/分块写接口逐个补齐（这些在 Java 侧是 internal 接口，不经过拦截器）。审计失败静默降级，不阻断业务。

### Q8: 员工端知识库权限漏洞是怎么发现和修的？
> 代码审查发现员工聊天页直接复用了管理端的全量文档列表接口——无权限过滤，管理级知识库文档对所有人可见，且暴露了增删改入口。修复：新建员工侧只读浏览接口，用与对话链路同一套知识库可见性解析（fail closed）过滤，文档分块预览按 KB 归属二次校验（越权 403），搜索强制限定授权范围，删除全部写操作入口。教训：前端页面"长什么样"应由后端数据边界决定，而不是反过来。
