# 落地方案：组织制度与合规助手（私有化交付）

> 目标形态：**可举证的 Agentic 制度助手**——嵌入客户 OA / 企业微信 / 钉钉，回答 HR / 财务 / 行政 / IT 制度问题，给出原文出处，并能直接发起申请或工单。
> 交付模式：**私有化、单客户独立部署**（不做多租户，这是本方案最大的成本节省项）。
> 首发垂直：**通用组织制度与合规**（HR + 财务 + 行政 + IT），语料形状与 `data/documents/` 现有 6 篇一致。

---

## 一、目标客户与价值主张

**客户画像**：200 人以上、制度文件 200～2000 篇、有内审/合规/上级检查压力的组织。制造、医院、银行支行、高校、政府下属单位都符合。

**一句话价值主张**：把员工手册变成 7×24 答疑，且**每条答复都能指向原文、每次提问都能被审计**。

**为什么客户会付钱**（三个可量化痛点）：

| 痛点 | 现状 | 交付后的指标 |
|---|---|---|
| HR/IT/财务被重复问题淹没 | 电话、群里反复问 | 一次解决率、转人工率 |
| 新员工上手慢、制度找不到 | 靠老员工带 | 首次提问到解决的时间 |
| 内审/检查要求"答复可追溯" | 人工答复无留痕 | 引用准确率、审计日志完整率 |

**不要打的牌**：功能广度。Dify / FastGPT / RAGFlow / 扣子 都开源免费，比不过也不该比。差异化只在三点——**可举证、可私有化、能办事**。

---

## 二、交付形态

**部署拓扑**（沿用现有 `docker-compose.yml` 六服务，私有化单机即可）：

```
客户内网
├── nginx(统一入口 :80)  ── /        → 员工聊天页
│                        ── /admin   → 管理台（仅管理员网段）
│                        ── /api/    → backend:8001（SSE 直通）
├── backend  (FastAPI :8001)   LLM 编排 / Self-RAG / Agent
├── rag-engine (Spring :8002)  检索 + 解析 + 向量化（ONNX 本地）
├── mysql / redis / qdrant
└── 私有 LLM（vLLM / Ollama / 国产模型，OpenAI 兼容端点）
```

**关键点**：Embedding 在 Java 进程内用 ONNX 跑（[rag-engine/Dockerfile](rag-engine/Dockerfile#L26) 已把模型打进镜像），**只有生成这一步出网**。换成客户内网的私有模型后，**全链路可离线**——这是政企/金融/医疗的准入门槛。

**用户入口与角色**：

| 角色 | 入口 | 能做什么 |
|---|---|---|
| 普通员工 | OA/IM 里的聊天页 | 提问、看引用、点👍/👎、转人工 |
| 知识管理员 | 管理台 | 传文档、管切片、看热文档与差评 |
| 合规/内审 | 管理台（只读） | 查审计日志、导出问答记录 |
| IT 运维 | 管理台 | 限流、敏感词、API Key、监控告警 |

| Agent 工具链（ReAct + 9 工具） | [core.py](backend/agent/core.py) | "查完直接开工单"的基础 |

|---|---|---|---|---|

| 2 | **修 nginx 硬编码路径** | [rag-assistant.conf](deploy/nginx/rag-assistant.conf#L88) 三处写死 `D:/RAG-study/rag-admin/dist`，任何 Linux 客户环境都跑不起来 | 改为容器内路径 `/usr/share/nginx/html`，用变量或 `root` 指令统一 | 1 |

| 4 | **私有 LLM 实测打通** | 政企/金融准入的硬门槛；现在只对接过 DeepSeek 公网 | `DEEPSEEK_BASE_URL` 已是 OpenAI 兼容端点，接 vLLM/Ollama/国产模型后需实测三条链路：普通对话、**工具调用**（多数私有模型 tools 支持较弱）、SSE 流式。[utils/http_client.py](backend/utils/http_client.py) 可能要加 tool-call 兼容分支 | 2–3 |
| 5 | **统一入口 + 强制登录** | 现在 80 端口是管理台、聊天页在 8001，客户会当成两个系统；且 [chat.py](backend/routes/chat.py#L392-L406) 的 `guest` 模式**不走检索**，暴露给客户毫无意义还会引起误解 | nginx 反代 `/`→聊天页、`/admin`→管理台；关掉 `guest` 路由或置于独立开关 | 2–3 |
| 6 | **License / 授权机制** | 全仓库无任何授权代码（已确认 grep 无命中）。私有化交付需要有效期 + 机器绑定 | 新增许可校验模块（Java 侧校验 + 启动自检），签发工具留在你手里 | 3–5 |

**P0 累计：13–20 人日**（约 3–4 周，单人）

### P1 — 决定客户是否续费

| # | 项 | 为什么 | 改哪里 | 估算 |
|---|---|---|---|---|
| 1 | **OCR** | [KnowledgeBaseService.extractText](rag-engine/src/main/java/com/ragstudy/service/KnowledgeBaseService.java#L247-L250) 只用 Apache Tika，扫描件直接无文本。政企/医院/制造业的制度附件大量是扫描 PDF | 接离线 PaddleOCR 或 Tesseract；解析任务加"检测到无文本层 → 转 OCR"分支（`ParseTaskService` 已有异步任务框架可复用） | 5–8 |
| 2 | **Self-RAG 条件触发** | 现在只要检索到来源就**必跑第二次 LLM 调用**（[chat.py](backend/routes/chat.py#L238-L245)），成本与延迟直接翻倍 | 改为仅当 top1 分数低于阈值、引用数不足或答案过短时触发；加总开关与阈值配置 | 1–2 |
| 3 | **文档级 / 部门级权限** | 现在只到知识库级（`KbUserAccess`）。客户一定会提"薪酬制度只有 HR 能看，但 HR 制度全员可见" | 权限下沉到切片：Qdrant payload filter + BM25 结果过滤，检索层强制注入部门条件 | 3–5 |
| 4 | **评测集与回归** | `evaluation/` 下只剩 `.pyc`，`grader.py`/`run_eval.py` 源码已丢。**面对合规客户，"效果好"必须用数据证明** | 重建"问题 → 期望答案 → 期望引用"标注集（建议 200 条起）+ 回归脚本，风格可复用 [verify-p0.py](deploy/verify-p0.py) | 3–5 |
| 5 | **表格解析** | 制度文件里大量表格，Tika 出纯文本会丢结构，导致"报销标准表"答不准 | Tika 之外补表格抽取（PDF 用 `pdfplumber`/`tabula`，DOCX 用 POI 表格 API），表格单独成块并保留表头 | 3–5 |
| 6 | **SSO** | 现在只有本地账号。客户会要求对接 AD / LDAP / 企业微信 / OA 单点登录 | `routes/auth.py` + Java `AuthController` 增加 OAuth2/LDAP 分支 | 3–5 |

**P1 累计：18–30 人日**

## 六、验收指标

**技术指标**（交付验收单里要写死基线）

| 指标 | 目标 | 怎么测 |
|---|---|---|
| 检索命中率（Recall@5） | ≥ 85% | P1-4 评测集 |
| 引用准确率（答案确实来自所引分块） | ≥ 95% | 人工抽检 100 条 |
| P95 首字延迟 | ≤ 3s | 压测 |
| 单次回答成本 | 触发 Self-RAG 时 ≤ 2 次 LLM 调用 | Token 统计已有 |
| OCR 覆盖率 | 扫描件 ≥ 90% 可提问 | P1-1 后抽检 |

**业务指标**（决定续费）

一次解决率 · 转人工率 · 引用点击率 · 日均活跃提问人数 · 制度更新到生效时延

**特别建议**：把"**证据不足警告触发率**"作为一项正式指标报给客户的合规部门——这是你相对所有红海产品的独有卖点，而且数据你已经在生成。

## 八、风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 通用知识库是红海 | 被免费开源产品比价 | 绝不比功能广度；只讲"可举证 + 可私有化 + 能办事"，演示时直接打开审计日志与引用原文 |
| 客户要求"必须用我们的私有模型" | 工具调用链路可能不通 | P0-4 提前实测；同时保留"无工具调用的纯 RAG 模式"作为降级 |
| Self-RAG 成本翻倍 | 规模化后预算超标 | P1-2 改条件触发 |
| 效果无法证明 | 验收被卡 | P1-4 评测集是**最容易被挑战的点**，优先级应提到 P1 首位 |
| 单客户定制陷阱 | 第二个客户要重做 | 定制一律走配置（阈值、权重、敏感词、权限），代码保持"换语料不换代码" |
| 交付后无人运维 | 口碑受损 | 备份/巡检脚本 + 运维手册纳入交付物 |

## 十、立刻可做的三件事

1. **P0-1 离线包**：这是目前唯一的**硬阻断**——不解决，第一个客户现场就卡住。
2. **P1-4 评测集**：需要客户语料才能做，但要提前准备标注工具与脚本模板。
3. **演示脚本**：把"提问 → 引用原文 → 显示证据不足警告 → 查审计日志 → 一键转工单"串成 5 分钟演示。现有功能已足够支撑，不需要新开发。
